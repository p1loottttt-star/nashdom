## Э2. Supabase на рост
**Миграции.** `supabase/` становится проектом Supabase CLI: `config.toml` + `migrations/`. Первая миграция — текущая схема с правками ниже (облачных данных ещё нет, переносить нечего). Применение: `npx supabase db push` в тестовый, потом в прод (команды — Ване).

**Изменения схемы.**
- `items.id` — новое правило; `items.data` — до 1 МБ (рисунки записок помещаются).
- Квоты: строк `items` на пару ≤ 20 000; фото на пару ≤ 3 000; сообщений чата ≤ 30 в минуту на человека. Триггеры с понятной ошибкой (`quota`), клиент показывает тост.
- Индексы: `ledger (couple_id, reason, created_at)` под дневные пределы начислений.
- `ledger.user_id` и `messages.user_id` — `on delete set null` (баланс пары не меняется, когда человек удаляет аккаунт).

**Realtime: широковещание из базы.** Подписки `postgres_changes` убираются. Триггеры `after insert/update/delete` на `items`, `ledger`, `messages`, `members`, `profiles`, `couples` вызывают `realtime.send(..., 'couple:<id>', private => true)` — в тот же закрытый канал пары, где уже живут присутствие и плеер (RLS на `realtime.messages` уже пускает только двоих). Событие `db`: `{ t: таблица, op, row }`. Если `items.data` больше 100 КБ — строка уходит без данных, клиент дочитывает её сам (как сейчас с `errors`). Профиль шлётся в канал пары его владельца. Отсев эха своей записи — как сейчас (`updated_by` + `updated_at`).

**Закрытые фото.** Корзина `house` — `public = false`, чтение — только участникам пары (папка = `couple_id`). В данных хранится ссылка-путь `sb:<путь>`, а не адрес. `store.mediaUrl(ref)` — синхронный: при входе все пути из данных подписываются пачками (`createSignedUrls`, 7 дней), новые загрузки — сразу; раз в сутки пересписываются. Обычные `https:`/`data:` проходят как есть (локальный режим, стартовые данные). Затрагивает галерею, стену с фото, альбомы, аватары.

**Удаление и выгрузка.**
- «Выгрузить мои данные» — JSON со всем, что видно человеку (дом, баллы, чат, профили, список фото), скачивается из браузера.
- «Удалить аккаунт» — RPC `delete_me()`: удаляет пользователя (профиль и членство — каскадом). Если в доме больше никого — клиент сначала удаляет файлы папки пары через Storage API, потом RPC удаляет дом целиком. Если партнёр остаётся — общий дом остаётся у него, мои сообщения удаляются, строки баллов теряют автора.

**Проверки облака.**
- SQL-тесты на PGlite (Postgres в Node, без Docker): заглушки `auth.uid()`, ролей и `realtime.send`; проверяют изоляцию пар (пара Б не видит и не пишет в дом А), начисления и пределы, покупку и подарок, вход по приглашению (не больше двоих), квоты, правила id, `delete_me`.
- Сквозной тест в CI: `supabase start` (локальный Supabase в Docker на машине GitHub), миграции, две пары по две учётки через supabase-js: записка, ход в игре, тест с `:` в id, подарок — у партнёра приходит через Realtime; фото по подписанной ссылке открывается у партнёра и не открывается у чужой пары. Локально у Вани Docker нет — этот тест идёт только в CI.

## Э3. Наблюдаемость
- Таблица `client_errors` (время, версия, пользователь, пара, сообщение ≤ 500, стек ≤ 4 000, адрес, браузер). Писать могут все (и до входа), читать — только из панели Supabase. Триггер-предохранитель: не больше 300 строк в минуту на всю таблицу, старше 30 дней удаляются (pg_cron).
- Клиент: `error` и `unhandledrejection` → одна запись на одинаковую ошибку за сессию, не больше 20 за сессию. В локальном режиме — только консоль.
- Vercel Web Analytics (без cookies, баннер не нужен): включает Ваня в панели, на сайте — `@vercel/analytics`. Продуктовые числа (пары, активные за неделю) — SQL-запросы в `supabase/queries.sql`.
